quakewang (Rust 歴 9 年) 言う。AI 時代、Rust より Zig 推す。

- Rust の借用チェッカー、昔は人間プログラマの保険。人間コード書かない時代、足かせ。
- AI は秒で試行錯誤したい。Zig 0.17 以降、増分コンパイル、書いて 1 秒でテスト回る。
- Rust だと AI、コンパイルエラー何度も読む。無理な迂回する。struct / trait / ライフタイム散らかる。増分ビルド 10 秒超。数十倍遅い。
- Zig はアロケータ明示で引数渡し。境界はっきり。C ライブラリそのまま呼べる。
- 「AI とコンパイラが戦わなくていい」設計が強い、と主張。

## 議論 1: Zig はまだ 1.0 前

- リリースごとに stdlib と build.zig 壊れる。0.15 の I/O (Writer / Reader) 刷新が大きい。
- async/await は一度言語から消えた。
- でも C 資産との相性、一番の強み。
  - `zig cc` / `zig c++` = clang ラッパー。クロスコンパイル一発。
  - build.zig で C もビルドできる。
  - `@cImport` で C ヘッダ直接読む。
- 「ツールチェーンとして Zig 使う + ユーザー側コードだけ Zig」は現実的。言語破壊変更の影響も小さい。

## 議論 2: AI は Zig 書けるか

書ける。でも古い API 出しがち。

- 学習データ少ない。大半は旧バージョンのコード。
- 存在しない関数、旧シグネチャ、自信満々に出す。
  - `std.io.getStdOut()` 系
  - ArrayList の managed / unmanaged 混同
  - 旧 build.zig API
- 対策:
  - Zig バージョン固定
  - 該当バージョンの stdlib ソース / ドキュメントを context に入れる
  - コンパイラエラーで自己修正させる (ここは増分コンパイル速いの効く)

## 議論 3: メモリ安全性と速さ

「Zig 速いのは安全性ないから」は半分違う。

- 実行速度: Rust のチェックは主にコンパイル時。実行時コストほぼゼロ。Zig と Rust、実行性能ほぼ同じ。
- 差が出るのはコンパイル速度。借用チェッカーなし、独自バックエンド、増分コンパイル。
- Zig も Debug / ReleaseSafe では境界チェック、オーバーフロー検出あり。ReleaseFast で外すと安全性消える。

AI が Zig で出しやすいバグ:

- use-after-free、double free、リーク
- ArrayList 再確保後、古い要素ポインタ使い続ける
- `defer` / `errdefer` の置き忘れ、順序ミス
- スタックのローカル変数ポインタ返す
- アロケータ取り違え (別のアロケータで free)

LLM はグローバルなライフタイム推論が苦手。局所で正しく見えて、呼び出し跨ぐと壊れる。

緩和: DebugAllocator (旧 GPA) / `std.testing.allocator` でリーク・double free 検出。ただし実行された経路だけ。テストカバレッジ前提。

## 議論 4: JS vs TS の類比

「AI 完璧だからガードレール不要」は「JS で書けば TS 不要」と似てる。かなり当たってる。

- ガードレール = 人間のミス防止だけじゃない。**AI 出力を機械的に検証する基準**でもある。
- AI 時代は人間レビューがボトルネック。コンパイラ保証が広いほど、レビュー範囲が狭くなる。Rust 借用チェッカーの価値はここ。
- ツイートの本質は「検証コストが高すぎる」指摘。ガードレール不要論とは別。コストと保証のトレードオフ。
- 類比が崩れる点: TS 型チェックはほぼ無料。借用チェッカーは設計に制約を課す。AI 苦戦の理由もここ。

## 結論 (自分用)

- テスト / サニタイザ / Debug アロケータで担保できる体制あるなら Zig 成立。
- 体制なければ Rust の方が総コスト低い。
- Zig の本領は「C 資産 + クロスコンパイル + 軽量ツールチェーン」。AI 向きかは API 安定待ち。
- 0.17 の増分コンパイル速度は、ツイートの主張そのまま。未検証。
