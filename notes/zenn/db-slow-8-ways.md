Oracle 前提。DB チューニング前の、書き方・テーブル設計の注意。初心者向け。他 RDB でも通用。

## 読んだ 5 個

- 大量の逐次コミット
  - 数倍〜十数倍遅い。10分バッチが1時間超える。
  - 理由: 書き込み毎に WAL / REDO ログ + INDEX 再構築。
  - 目安 1000〜1万件ごとコミット。要計測。大量 DELETE は TRUNCATE 検討 (ロールバック不可)。
- バッチ分割の疑似並列インサート
  - 参照・ファイル書き込みは効く。RDB 書き込みは効かず、DB 全体を遅くする。
  - RDB は参照重視設計。書き込み時の最適化が並列に弱く競合する。
  - 対策: パーティション / シャーディング、パラレル DML。元データは PK でソート。
- 全カラムに INDEX
  - 最小限にせよ。書き込み遅くなる。マイグレーション時に死ぬ。
  - 1つ目のキーで 1000件以下に絞れれば十分、が筆者感覚。
- シーケンス番号を PK
  - シーケンス生成が詰まる、並列で同期が要る、Right Growing Index (B-Tree 右端リーフに書き込み集中)。
  - 対策: キャッシュ増、ハッシュパーティション、シャーディング、単調増加値を INDEX にしない。筆者は最初から UUID 推し。
  - ただし UUID を避けるとクラスタ INDEX で速い場合もある、と注意書きあり。
- カーディナリティ低いカラムに INDEX
  - 効果なし。デメリットだけ。

## 残り 3 個 (本文の断片から。通読してない)

- サマリーテーブルを作るな。必要なら SQL 集計 or Materialized View。
- 巨大テーブルへの書き込み設計はボトルネック。
- 処理は原則 RDB 側 (サーバサイド) でやれ。

## 補足 (記事外。会話で整理した内容)

- カーディナリティ = 列の値の種類の多さ。Boolean は低い、UUID は最大。
- UUID 列の INDEX は 1 件検索に最適。ただし UUIDv4 は挿入位置がランダムで、B-Tree のページ分割・キャッシュ効率悪化。
  - InnoDB のようにクラスタ INDEX が PK の DB で UUIDv4 を PK にすると遅くなりやすい。記事の注意書きはこれ。
  - 折衷案 UUIDv7 (時刻順)。局所性とホットスポット回避を両立しやすい。
- Boolean でも偏りが大きければ有効。99% false で true だけ探すなら部分インデックス (PostgreSQL の partial index 等)。50/50 なら無意味。
- n:n 中間テーブル
  - カーディナリティはテーブル種別でなく列ごと。`user_id` なら「ユーザー数」ぶんの種類。
  - `(a_id, b_id)` 複合 PK / UNIQUE は必須級。逆引きあるなら `(b_id, a_id)` も。複合 INDEX は左端列からしか使われない。
  - 書き込み多いなら INDEX は 2 本まで。
- シーケンス PK の問題は「連続して書かれる」こと (書き込みが右端リーフ 1 か所に集中)。DynamoDB のホットパーティションと同じ原理。
  - 読みは連番が逆に有利 (範囲スキャン、キャッシュ局所性)。
  - 単一ノード RDB では顕在化しにくい。Spanner / Aurora マルチ書き込み / Oracle RAC など分散環境で効く。
- 逐次コミット回避、バルク、INDEX 張りすぎ注意は定番。記事の価値は「なぜ遅いか」(WAL / REDO、INDEX 再構築) の説明。
