## 主張

人間の仕事 = 実装ちがう。評価指標つくる、ループつくる、AI の動き見る。

## 人間の役割

- モデルに無茶振りして、できる/できない観察。ドメイン知識にためる
- ループ作る。自動化で浮いた時間 → 指標改善に使う
- 評価指標作る。どの数値上げる？トレードオフどっち優先？
- AI 行動ログ見て、指標ちゃんと追ってるか確認
- テスト/CI 調整。指標増える → CI 長くなる → 何捨てるか決める

## 考える順番

1. AI に任せられる？ダメならブロッカー何？
2. 完了定義と指標は？数値にできれば自動化できる
3. 一回やらせて観察
4. 人がつきっきりでなくても判断できる基準、作れるか
5. 失敗したら原因切り分け
   - コンテキスト不足 → 指示、守らせるテスト足す
   - 権限不足 → 権限やるか考える
   - 性能不足 → 待つ。モデル進化が解決

## アンラーニング

- 「優秀なプログラマとして振る舞え」「深呼吸して」 → もう効かない
- AGENTS.md に書くのは一般論ちがう。**選択肢複数あるときの判断基準**
  - 原文の例:
    - `node は 24+ を使う`
    - `既存のプロジェクトの設計は尊重しつつ、新規には npm ではなく、pnpm を使う`
    - `nix を使う/使わない`
    - `Rust は stable の 1.99 を使う`
    - `gh stack を使う`
  - AI が迷う、古い知識で選ぶ場面を先に決めとく
  - 原文いわく、グローバルプロンプトは基本あまり書かない。書くならこの手の判断基準だけ
- モデル知識は半年くらい古い → プロンプトで補う
- skills は重点学習される → 陳腐化はやい
- コンテキストの情報 > モデル内の世界知識
- 有名 OSS で組むとモデルが知ってるから効率いい
- `/compact` は判断基準ないと変な方向に偏る。注意

## 既存リポジトリに入れるとき

- まず「今の構成読んで解説して」→ 自分の理解とズレ確認
- 変わったこだわり、制約は AGENTS.md へ

## ループ

- **原始 Ralph Loop**: シェル無限ループで `claude -p`。Git 履歴見て次やること決めさせる
  ```bash
  while :; do
    claude -p "Git 履歴を見て次にやることを探して"
  done
  ```
  - 毎回プロセス新規起動 → コンテキスト毎回リセット。引き継ぎは Git 履歴だけ
  - 終了条件の記述なし
- **/goal**: `/goal Issues を全部潰して`。ゴール満たすまで自走
  - 記事は「セッション終了のたび再送」と読めるが、公式ドキュメント (https://code.claude.com/docs/en/goal) だと実態ちがう
  - 実態: session-scoped な prompt-based **Stop hook** のラッパー。**同じセッション、コンテキスト保持**のまま継続。リセットしない
  - ターン終了のたび、別の小型高速モデル (evaluator) が条件判定
    - 未達 → 次ターン自動開始 (理由が次の指針)
    - 達成 → 解除
    - 不可能 → 失敗理由つきで解除
  - evaluator はツールもファイル読みもしない。会話に Claude が出した内容だけで判定 → 条件は Claude の出力で示せる形で書く
  - 条件: 測定可能な終了状態 + 確認方法 (例: `npm test` が exit 0) + 制約。最大 4000 文字
  - `or stop after 20 turns` のようなターン上限を条件に入れるの推奨 (既定上限の記載なし)
  - `/goal` で状態確認、`/goal clear` で解除、`claude -p "/goal ..."` で非対話
  - 数ターン連続でツール未使用 → 警告して停止
  - 認証失敗、クレジット枯渇などは自動解除。過負荷系は最大 3 回リトライ
  - `/clear` でゴールも消える。`--continue` / `--resume` では復元
- **dspy / RLM** (実験): ワークフロー決まってるとき、巨大コンテキストをコード断片に分解
  - 参考: https://dspy.ai/current/api/modules/RLM/
- **マルチエージェント** (実験): 決定的な答えまだ無い。無理に使うな。干渉少ないレーンに分けてサブエージェント割り当てならあり
  - プロンプト例: 「今あるタスクから、干渉が少ないものをレーンに分割して、レーンごとにサブエージェントを分割して」
  - 参考論文: https://arxiv.org/abs/2512.08296

## 探索的改善

エージェントを信じて丸投げ、改善点探させる。

- 今の実装と最新研究を比べて参考になるもの列挙
- SRE 視点でテレメトリ計装
- テスト壊さずリファクタ
- DB の N+1 探して潰す
- セキュリティ視点で攻撃チェックリスト作り、localhost で侵入テスト (Docker サンドボックスでやる)

大事なのは「**誰にとって、何の数値が大事か**」。これが改善の理由になる。

見つかった項目 → Umbrella Issue にまとめる → /goal で順番に消化。

自分の専門外 → maintainer-persona スキル (メンテナの人格、好みを学習) でレビューさせる。

## /goal と組み合わせる評価指標

決定的に測れるやつ優先。CI で不安定なパフォーマンスベンチより RSS や Fuel。

- メモリ使用量 (RSS)、hyperfine、perf、valgrind
- lint 警告数 (循環的複雑度 = cccc)、コード重複率 (similarity)
- Mutation Test の kill 率
- VRT (ビジュアル回帰テスト) 一致率

主観の指標 → 人間が毎回呼ばれる → ダメ。数値にしろ。

## 理解する

- 全コード読むの無理。E2E ケース名、テストコード、関数シグネチャだけ見て振る舞い掴む
- eli5 / explainer スキルで概念解説させる
- 解説画像を `gh --attach` で PR に貼る

## マージ自動化 (実験)

- OpenAI が AI トリアージでマージ一部自動化してる事例
- 安全なコード → AI がマージ
- DB スキーマ変更、terraform 変更 → 人間にエスカレーション
- 著者もレビューツール開発中

## 形式手法

実装しようとしてる**仕様そのもの**が正しいか検査する。依存型、時相論理など。

ツール使い分け:

- マイクロサービス、マルチスレッドのキャッシュ制御 → TLA+ / Quint (経験上、漏れ出やすい)
- 述語論理で書ける制約 → Z3
- 困ったら Z3 か TLA+
- アルゴリズム開発 → Lean
- ユーザー権限まわり → Alloy

自然言語をそのまま形式仕様にするわけじゃない。性質を書くイメージ。

実例:

- 既存コードの形式化できる部分を形式化 → テストオラクルにして実装が従ってるか確認
- モデル検査の反例 → 実際のテストケースに落とす
- 検査内容をドメイン用語なしで、たとえ話で説明させる
- 仕様化スキル: formal-methods-reconciler

## 結論

AI コーディング手法は変化はやい。今の手法は暫定。「またすぐ変わると思います」。

軸は変わらない: 具体的な指標 → ループで自動化 → 人間は判断基準と観察に集中。
