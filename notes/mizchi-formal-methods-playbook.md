# 1. 原文のニュアンス

## 核となる主張

- 仕様書が無い、あてにならない、仕様と実装がずれている現場が前提。
- **既存の実装を「事実上の仕様 (de-facto spec)」とみなして形式化する**手順書。
- 狙い: テストでは踏めないバグと、実装が暗黙に決めている仕様を炙り出す。
- 3 段:
  1. **吸い出し (extract)**: 実装が主張している仕様と、暗黙に決めている挙動を分けて抜く。
  2. **形式化して反例探索 (refute)**: 主張をモデル化し、全入力や全順序で成り立つかを機械に攻撃させる。
  3. **突き合わせ (reconcile)**: 出た反例を、ドメイン知識のある人に「意図か?」とぶつける。意図なら仕様として明文化、意図でなければバグ。
- 著者の意見: 反例は、バグ報告であると同時に**認識合わせの会話の起点**。ここが最も効く。最終成果物は証明の山ではなく、「実装の主張 / 検査結果 / 確認質問」の**台帳**。形式手法は、バグ検出だけでなく、仕様と認識を揃える共通言語。

## 実装を読むときの 8 つの問い (§3)

1. 空や未設定のとき、何が起きるか。
2. エラーや取得失敗のとき、true、false、例外のどれか (fail-open / fail-close)。
3. 否定 (NOT、除外、inverse) をかけると、上の答えはどう変わるか。
4. 境界は `>` か `>=` か。端点は含むか。
5. 同時に 2 つ来たら、片方の結果がもう片方に間に合うか。
6. 値は誰が決めるか。信頼できない相手が差し替えられるか。
7. ループや引き上げは何で止まるか。止めている条件は本質的か、偶然か。
8. 2 つのシステムは、このデータ (レイアウト、enum、単位) で合意しているか。

宣言された仕様の在り処: コメント (特に「なぜ」を語るもの)、テスト名とアサーション、ガード節、panic、error 返し、enum と定数テーブル。「元からそうだった」系のコメントは「化石 (fossil)」と呼び、仕様か惰性か確認する。

## 道具の使い分け (§1)

- **Z3 (SMT)**: 全入力に対して、ある一瞬の性質。純粋な述語、設定やルールの整合性。モデルとコードのギャップは狭い (データなら実データを直接食わせられる)。保存時の validator、CI の静的検査に置く。
- **TLA+ (TLC)**: 時間を通じて、全順序、全 interleaving。ステートフルなプロトコル、並行、クラッシュ後。ギャップは広い (命令型は手で抽象する)。設計レビューの成果物、回帰ガード。
- **素の全列挙**: 状態空間が有限で決定的なら、プログラムで直積を回すのが最も安い。ツールを持ち出す前に「有限か? 決定的か?」を問う。
- 判定: 「どんな入力でも成り立つか」「この設定は配信され得るか」→ Z3。「どの順番でも大丈夫か」「同時に来たら」「クラッシュ後は」→ TLA+。
- 本文に Alloy、property-based testing、他のモデル検査器は出てこない。

## バグ型カタログ (§2)

設定やルール系 (Z3 向き):
- 矛盾設定 (dead config): 条件の連言が充足不能。`A のみ ∧ A を除外`、`開始 > 終了`、`x>20 ∧ x<18`。
- 冗長、包含 (subsumption): 「上限 10 回 ∧ 上限 1 回」で、きつい方が支配して片方が効かない。実効値を算出して警告。
- 被覆の穴、dead branch: どの選択肢にもマッチしない入力、選ばれない枝。
- 変更の差分影響: 設定編集で判定が変わる入力を摘出。
- 表現の等価性: 旧形式と新形式、リファクタ前後が全入力で同じか。

並行、時間系 (TLA+ 向き):
- read-modify-write レース、TOCTOU: 読んで判定して書くが分離していて、両者が古い値を読んで両方通る。
- 判定と記録の分離: 判定は即時、記録は非同期で、上限をすり抜ける。
- 結果整合 (staleness): 並行が無くても、書いた値が見えるまでの遅延だけで上限が破れる。
- 原子性、torn read: 途中状態を読む。「別ファイルに書いて rename」と「in-place 上書き」の対比。
- カウンタの不変条件: 重複配信や並行下で負にならないか。
- 収束、runaway: リトライや引き上げが有界回で止まるか。外部条件 (期限など) だけがブレーキになっていないか。
- 伝搬、最終整合: crash と再起動で更新が失われないか。edge-trigger は失いうるが、level-trigger は追いつく。
- 冪等性: リトライで二重カウントしないか。送信ごとにランダムな ID を作ると重複記録になる。

境界、信頼系 (どちらでも):
- fail-open / fail-close の不一貫: 情報が取れないとき、ある機構は全落ち、別の機構は素通り。
- **エラーを boolean に畳むことと否定**: 「不一致」と「エラー」を同じ false に畳む実装で否定をかけると、エラー時にマッチする。著者は「最も見落とされやすい」と述べる。
- 空集合の意味: 空の AND が真 (常時マッチの backdoor)、空の OR が偽、要素ゼロが真、が階層で不整合。
- 信頼境界と詐称: クエリパラメータやヘッダなど、利用者が自由に付けられる値が、検証なしに「信頼された値」として優先採用される。
- クロス境界の表現契約: hourly と 15 分、MSB-first と LSB-first など。変換の全単射性。
- クライアント側だけの検証: UI だけが弾き、API は素通し。
- 欠けた前提条件: 負のサイズや空配列で panic。ガードが呼び出し側にしかない。

## 運用と台帳 (§8)

1. 対象領域を選ぶ (バグ型カタログで「ありそう」な箇所)。
2. 実装を読み、宣言された仕様と暗黙の挙動を分ける。8 つの問いを機械的に投げる。
3. 決定関数 `predict` と invariant を書く。証明したいのか、反例が欲しいのかを先に決める。
4. ツールで回す (Z3、TLA+、全列挙)。
5. 反例が出たら、witness (具体値) 付きで「意図か?」をドメインに問う。成立したら、契約 (regression guard) としてロック。
6. CI に載せる。self-check、broken-variant、宣言的な依存管理 (nix flake や lockfile)。
7. 必要なら trace-checking (実ログとモデルの突き合わせ)。
8. 限界効用で止める。台帳を残す。

- self-check: 各モデルに期待判定 (VIOLATE / OK) を持たせ、一致するかを assert する。
- **broken-variant** (わざと壊した版) には「VIOLATE が出るはず」と期待する。OK が出たら、何も検査していない緑。

## 限界と注意 (著者の記述)

- 形式手法が検証するのは「書いたモデル」で、コードそのものではない。データ (設定やルール) ならギャップは狭く、命令型や並行コードは広い。
- 向かない: 確率的な性質 (期待値、分布)、制御理論的な性質 (PID の収束)、既に単体テストで総当たり済みの最適化アルゴリズム、主要な不変条件を押さえた後の確認的な命題の量産。
- アンチパターン: 直列依存を無理に並行としてモデル化する、実装を読まず記憶や要約からモデルを組む (変換テーブルを 1 つ取り違えると偽の証明)、broken-variant なしで「緑だから OK」、ネットワークや手動設定に依存した検証。
- 主要な穴を押さえた後は、新しい形式化より、溜まった反例をドメインの人と捌くほうがレバレッジが高い。

# 2. わかりやすく言い直した版

## 状況

- コードは動いている。でも、ドキュメントは古いか、無い。
  - 速度重視で書き散らして、動くが「なぜ動くか」が分からない。
  - ドキュメントはあったが、バグ修正と仕様変更を重ねるうちに、コードとずれた。
- 「正しい動き」が分かるのは、コードだけ。だから、**コードが事実上の仕様**。

## 記事の発想

1. コードを読んで、「こういうルールで動いているようだ」と書き出す。
2. そのルールを機械に渡して、**ルールどうしの矛盾や抜け穴**を探させる。
3. 見つかったものを、仕様に詳しい人に見せて、「意図したもの? バグ?」と聞く。

## 例

- 設定に「同じ人は 1 日 10 回まで」と「同じ人は 1 日 1 回まで」がある。後者が効いて、前者は意味を持たない。後から足して、前のルールを消し忘れたのかもしれない。人間が眺めても気づきにくいが、機械に「両方を満たす場合は?」と探させると、**実質 1 回**と判明する。人に「10 回のほうは消していい?」と確認できる。
- 条件が「ユーザーが禁止リストに**ない**」。禁止リストの取得に**失敗**したとき、コードは「リストにない」扱いにする。するとエラーのときに**誰でも通れる**。テストで偶然試さない限り見つからない。「8 つの問い」(エラーのときは? 否定をかけたら?) は、このバグを見つける質問。

## 一番価値があるのはどこか

- Z3 や TLA+ は「機械に探させる道具」の名前。中身を知らなくても、考え方は分かる。
- 価値が大きいのは、手前の部分: **「コードを読んで、ルールを書き出し、人に確認する」流れ**。
- 道具を使わなくても、8 つの問いをコードレビューで投げるだけで効果がある。
- 「仕様が無い」現場では、まず「コードは何を決めているか」の一覧を作るだけでも価値がある。その作業は LLM に手伝わせやすい (「このコードの暗黙のルールを書き出して」「エラーのときの挙動は?」)。
- 考え方は、既存プロジェクトから DESIGN.md を逆起こしする発想 ([[design-md-getdesign]]) と近い。

# 3. 用語集

(一般的な知識に基づく説明。今回のセッションでは調べていない)

- **形式手法 (formal methods)**: 仕様や性質を数学や論理の言葉で厳密に書き、機械的に検証する手法の総称。テストは「試した入力」までしか言えないが、「全ての場合で成り立つ」を論理的に確かめることを狙う。Z3、TLA+、Alloy、Coq、Lean などを含む。書く手間と専門知識が要るので、航空宇宙、暗号、OS、クラウド基盤など、故障の代償が大きい分野で使われてきた。記事は、その中の軽量で実用的な部分だけを使う。
- **SAT**: 真偽値の変数を使った論理式が、真になる割り当てはあるか、を判定する問題。
- **SMT (Satisfiability Modulo Theories)**: SAT を拡張して、整数、実数、配列、ビット列、文字列などの「理論」を扱えるようにしたもの。結果は、SAT (成り立つ。例の値を返す)、UNSAT (どうやっても成り立たない)、unknown (判定できなかった)。矛盾設定の検出は、UNSAT を返させることで行う。
- **ソルバー (solver)**: 問題を与えると、答えを探して返すプログラムの一般名。SMT ソルバーなら、論理式を与えると、成り立つ値の有無を返す。
- **Z3**: Microsoft Research が作った、SMT ソルバーの代表的な実装 (オープンソース)。Python などから使える。全入力についての、ある一瞬の性質を判定する。時間を通じた状態遷移や並行処理には向かない。
- **TLA+**: Leslie Lamport が作った、システムの振る舞いを記述する仕様言語 (Temporal Logic of Actions)。「状態」「状態の遷移」「常に成り立つべき性質」を書く。コードではなく、設計の抽象モデル。並行処理や分散システムの「どの順番でも大丈夫か」の検討に使う。AWS が分散システムの設計検証に使った事例が有名。
- **モデル検査 / モデル検査器 (model checker)**: システムの状態遷移のモデルから、到達できる全ての状態を調べ、性質が破れる状態がないか確かめる手法とそのプログラム。破れる状態があれば、そこに至る具体的な手順 (反例の経路) を示す。ソルバーは「ある瞬間の論理式」を解き、モデル検査器は「時間とともに変わる状態の流れ」を全部たどる。
- **TLC**: TLA+ のモデル検査器。状態の数が増えすぎると調べきれない (状態爆発)。そのため、モデルを小さくして使う。
- **不変条件 (invariant)**: どの状態でも常に成り立つべき性質。「残高は負にならない」など。記事の記法では `NeverOverCap == served <= cap`。
- **反例 (counterexample / witness)**: 性質が成り立たないことを示す、具体的な値や手順。
- **VIOLATE / OK**: モデルの検査結果のラベル。VIOLATE は、不変条件を破る状態が見つかった (バグや反例がある)。OK は、どの状態でも成り立った。
- **broken-variant**: わざと壊した版。「VIOLATE が出るはず」と期待し、OK が出たら検証の仕組みが何も見ていない。テストでいう、失敗するはずのテストが本当に失敗するかの確認 (ミューテーションテストに近い)。
- **self-check**: 各モデルに期待判定を持たせ、実行結果と一致するかを assert する仕組み。
- **decidable fragment**: 解が必ず有限の時間で判定できる範囲の問題。記事は、述語が「区間、集合、等式」の範囲なら、Z3 が確実に答えを出せる、と言う。
- **interleaving**: 複数の処理の、実行順序の組み合わせ。TLA+ はこれを全て調べる。
- **TOCTOU (Time Of Check to Time Of Use)**: 条件を確認してから使うまでの間に、状態が変わってしまうバグ。
- **fail-open / fail-close**: 失敗時に、通す (open) か、止める (close) か。
- **trace-checking**: 実際のログを、モデルの正当な振る舞いの列と照合する手法。
- **PBT (property-based testing)**: 性質を書いて、ランダムな入力を大量に試すテスト。記事の本文には出てこないが、近い領域。
- **決定関数 `predict`**: 観測できる入力から結果を返す純粋関数。I/O、フレームワーク、DB を剥がして書く。

## 所感

- 注目点は 2 つ。8 つの問いは、形式手法を使わなくても、コードレビューやエージェントへの指示にそのまま使える。反例を人に見せて仕様の確認を引き出す発想は、LLM のレビューにも通じる。
- 道具 (Z3、TLA+) を実際に使うかは別の話。まず「暗黙のルールの一覧」と「8 つの問い」から試すのが現実的。

### この記事は何の実践か

- 目的は**バグ発見**。ドキュメントを起こすことが主目的ではない。確認済みのルールが台帳として残るのは副産物。
- 仕様書が無いと照らし合わせる基準が無い。そこで、コード自身の中の矛盾 (自分の主張と、実際の挙動のずれ) を探す。基準が無いので、最後に人間が意図を判断する工程が要る。
- テストケース作成のコツに近い。ただしテストと違う点が 2 つ。
  - 機械が全ての入力や全ての実行順序を調べられる (テストは人が選んだ入力だけ)。
  - 期待値を人が決めなくてよい場合がある (ルールどうしの矛盾を探すので、反例が出た後で人が意図を判断する)。
- 使い分け: 期待する動きが分かっていて確認したい → テスト。期待する動きが分からず、コード内の矛盾や抜け穴を探したい → この手法。

### 役割分担: ルールを書くのは人と LLM

- **Z3 や TLA+ は、コードからルールを書き出すツールではない**。書かれたルールを受け取って、矛盾や破れがないかを検査するだけ。
- ルールを読み取る労力は、人間や LLM が負う。変わらない。道具が肩代わりするのは、読み取った後の「全ての場合を調べる」部分。
- 記事の価値は、半分が**レビューの観点集** (8 つの問い、バグ型カタログ、宣言された仕様の探し方)、半分が**検査の枠組み** (道具の使い分け、台帳、broken-variant)。
- ルールの書式は 3 種類 (一般的な知識。記事にコード例はない):
  1. Z3: Python のコード (z3py)。または SMT-LIB (括弧だらけの S 式の標準形式)。
  2. TLA+: 専用の仕様言語 (`.tla`、数学記法に近い。`/\` は「かつ」)。TLC の設定ファイルは `.cfg`。
  3. 台帳: Markdown の表や箇条書き。形式は決まっていない。人間が読むためのもの。
- 流れ: (1) コードを読んで、ルールを自然文で書き出す (人か LLM)。(2) Z3 のコードや TLA+ に書き換える (人か LLM)。(3) Z3 や TLC が検査して、矛盾あり (UNSAT、VIOLATE) か、問題なし (OK) を返す。(4) 結果を Markdown の台帳に整理し、人に確認する。
- 難しい数式に見えるのは (2) の中間形式だけ。ここは LLM に書かせるのが現実的。考えるべきなのは (1) の自然文と (4) の台帳。

### LLM に出させる前提での使い方

1. LLM に 8 つの問いを渡して、コードから暗黙のルールを書き出させる。
2. 必要なら、LLM にルールを Z3 や TLA+ に書き換えさせて実行する。
3. 反例が出たら LLM が台帳にまとめ、人間が意図かバグかを判断する。

- 注意: LLM が書き出したルールが、コードの実態と合っている保証はない。記事も、「実装を読まず記憶や要約からモデルを組む」ことをアンチパターンとして警告。読み違えれば偽の安心になる。
- 対策: broken-variant で検査が本当に効いているかを確かめる。LLM が書いたルールを、人間が一度は目を通す。
- 最も手軽に価値を取れるのは、**8 つの問いとバグ型カタログを、プロンプトやチェックリストにする**こと。Z3 や TLA+ は、それで足りない場面が出てから考える。

### 未検証

- 手法を実際に試していない。用語集と書式の説明は一般的な知識で、記事の記述とは別。
