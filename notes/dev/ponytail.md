## 何者

ponytail.dev / github.com/DietrichGebert/ponytail

AIコーディングエージェント用ルールセット。過剰実装を防ぎ最小限コード生成させるプラグイン。DietrichGebert作、MIT。「54%コード削減、22%トークン削減、20%コスト減」を謳う（自称ベンチマーク値、公式実測ではない点は要注意）。

導入:
```
/plugin marketplace add DietrichGebert/ponytail
/plugin install ponytail@ponytail
```

## 仕組み

SessionStart hookでルール文をコンテキスト自動注入するだけ。魔法でもモデル改造でもない。CLAUDE.mdを毎ターン差し込んでるのと同じ原理、ただしユーザーには見えない裏側注入。

genshijinプラグインと同一構造（`hooks/hooks.json`→スクリプトのstdout出力→exit 0でClaudeへadditionalContext注入）。

## 判断ラダー7段階（コア）

書く前に上から順に判定、最初に成立した段階で止める:

1. 不要性検討 — そもそも要るか（YAGNI）
2. 既存コード確認 — プロジェクト内に同機能ないか
3. 標準ライブラリ活用 — 言語ランタイム標準で足りるか
4. ネイティブ機能 — 実行環境(ブラウザ/OS/DB)標準機能で足りるか（`<input type=date>`等）
5. 既インストール依存関係流用 — 新規追加せず既存活用
6. ワンライナー実装
7. 最小限の本実装

※stdlib(3)とnative(4)は「言語ランタイム」vs「実行環境」の軸違いなだけで精神は同じ。ラダーはフォールバック式→該当段階なければ次へ、言語のstdlib薄さで壊れる設計ではない。

**適用除外（削らない）**: 問題理解、入力検証、エラーハンドリング（データ損失防止）、セキュリティ、アクセシビリティ。ここは簡略化対象外。

## 強度モード

| モード | 挙動 |
|---|---|
| lite | 要求通り実装＋簡潔代案を1行提示（提案止まり） |
| full（既定） | ラダー自動適用、要件自体には口出ししない |
| ultra | YAGNI徹底、要件そのものに異議唱える |

`/ponytail lite\|full\|ultra\|off` で切替。既定はfull。

## コーナーカットと `ponytail:` コメント

ラダー段階7（最小実装）で「既知の上限ありの意図的簡略化」した場合のみ自動でコメント挿入。

```
ponytail: O(n²) scan; upgrade via indexing when dataset > 10k
```

条件: 意図的簡略化＋既知の上限(ceiling)＋アップグレード経路(upgrade)の3点セット。単なる手抜きバグとは別物。

**複数人開発での注意**: 実行に影響しないただのコメントだが、チーム未合意で導入すると「このマーカー何」と混乱招く。個人利用に留めるかチーム合意必須。PR出す前に`TODO:`へ機械置換する運用も手。

## 6スキル

常時自動発動:
- **ponytail** — メイン。コーディング全般に判断ラダー適用

能動的コマンド（スキャン系）:
- **ponytail-review** — 差分(PR)スキャン。タグ`delete/stdlib/native/yagni/shrink`で1行1指摘、末尾`net: -X lines`
- **ponytail-audit** — リポジトリ全体版review。差分でなく全体走査、削減効果順ランク付け

能動的コマンド（情報表示系、read-only）:
- **ponytail-debt** — `ponytail:`コメント収集、ceiling/upgrade明記チェック。未記載は`no-trigger`警告
- **ponytail-gain** — 公式ベンチマーク中央値を一度だけ表示。**このリポジトリの実測値ではない**、効果測定ツールではなく宣伝表示
- **ponytail-help** — 早見表

呼び出し関係なし、全部独立並列コマンド。

## 適用範囲

対応: 実装・リファクタ・コードレビューのみ。

非対応: 個別技術ドメイン知見（N+1問題、SQLインジェクション等の落とし穴知識は一切なし、判断ラダーは完全に汎用フレームワーク）、技術選定、調査、デバッグ/トラブルシューティング、アーキテクチャ設計。

## 実運用フロー

1. 実装時: plugin導入済みなら自然言語指示だけでラダー自動適用。コーナーカット箇所のみ`ponytail:`コメント付与
2. PR前: `/ponytail-review`で差分の無駄を再チェック（`/ponytail-audit`はPRレビューでなく定期棚卸し用途、別タイミング）
3. 負債確認: `/ponytail-debt`でコーナーカット箇所とupgrade条件棚卸し
4. gainは運用フローに入らない（宣伝表示のみ）

## 他プラグイン・CLAUDE.mdとの共存

スコープが「コード実装時の削減判断」1点のみと狭い→他ツールと軸が被りにくく組み合わせやすい。

- genshijin（文体圧縮）とは軸が直交＋思想同じ（無駄削減）→衝突しにくい、相乗効果寄り
- プロジェクトCLAUDE.mdが「防御的プログラミング徹底」等を指示してるとYAGNI方針と正面衝突しうる→この場合「思考力低下」というより指示の一貫性低下（ターンごとにどちらの制約優先するか揺れる）
- 複数プラグインのSessionStart hookは全部実行され出力は単純連結、優先順位機構はハーネス側にない。矛盾を感じたら片方offにして切り分けが確実
