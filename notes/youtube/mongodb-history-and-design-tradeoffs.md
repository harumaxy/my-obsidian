# MongoDBの歴史と設計トレードオフ

元動画: https://www.youtube.com/watch?v=6qGxTHy-nKM

## 誕生

2007年、DoubleClick出身エンジニア2人が広告配信の速度限界突破のため自作。
スキーマ不要・JSON (BSON) 保存・JS 親和性 → Node.js 登場と重なり MEAN スタック席巻。

## ブーム (2013〜)

「とりあえずMongo」時代。2017年 NASDAQ 上場。
ただしブーム初期から「なぜ速いか誰も説明できない」批判が存在。

## 黒歴史

### データ消失
- 初期仕様: 書き込み確認せずに成功を返す → 3年間放置 (〜2012年)
- Jepsen (2017): レプリケーション欠陥 → 多数決確定データが消失
- Jepsen (2020): 標準設定でサーバー切替時にロールバック発生
- MongoDB社は検証結果を都合よく引用 → 公開の場で批判された

### MongoDBアポカリプス (2016〜2017)
- 初期設定 = 認証なし・外部接続全許可
- Shodan で無防備インスタンス9万9千台発見
- 攻撃者が DB 丸ごと削除 → ビットコイン身代金要求
- 被害4万5千台以上、医療機関の患者記録20万件も人質
- v3.6 (2017) でようやく初期設定修正 → 公開から8年後

## 現在

v5.0以降は標準設定改善済み。年間売上20億ドル超の巨大企業に成長。ほぼ別物。

## 教訓

- **DB は「機能」ではなく「初期設定」で評価せよ** → ユーザーの9割は初期設定で使う
- スキーマレスは「スキーマ消滅」ではなく「アプリコードへ移動しただけ」。後払い

## ドキュメントDB 設計の本質

### 内部構造
- 保存形式: BSON (Binary JSON)。int/date/ObjectId など型情報を持つ
- 検索: フィールドに B-Tree インデックス → RDB と同仕組み
- JOIN 相当: `$lookup` (重い) か埋め込み設計

### 埋め込み vs 参照

| ケース | 推奨 |
|--------|------|
| 参照元が頻繁に変わる | 参照 + `$lookup` |
| 変わらない / 更新不要 | 埋め込み |
| 履歴として意味がある | 埋め込み (スナップショット) |

埋め込みは正規化不可 → 正本データが複数エントリと紐づく場合はデータ重複が発生。
「注文時点の価格」など変更不要なスナップショットなら埋め込みが正しいモデリング。

### MongoDB を選ぶ本当に正当なケース

- **ドキュメントの形が本当にバラバラ**: 商品カタログ (テレビとシャツが同テーブル) → RDB は nullable 地獄か EAV パターン
- **構造が階層ネスト前提**: CMS・フォームビルダー → RDB だとテーブル5枚 + 再帰 JOIN
- **Write-heavy ログ収集**: スキーマ検証より投入速度優先
- **Atlas Search / Vector Search**: 全文検索・ベクトル検索を DB 内に完結させたい場合

### 「スキーマが変わるから」は弱い理由

RDB + migration CI/CD で大体解決する。MongoDB を選ぶ実際の動機:
- チームが SQL 書きたくない
- Atlas マネージドが楽
- 上記の「形がバラバラ」ユースケースに本当に該当する

**RDB がデフォルト正解。MongoDB は特定ユースケース専用。**
