## 概要

Cに挑んだ2言語対比二部作の後編。前作Nimは上へ拡張(機能・表現力盛る)、Odinは横へ再構築(単純さ貫く)、対比構造。

## Odinとは

- 2016年、Ginger Bill氏がC++の不満から開発開始。フォークでなくゼロから作り直し
- 影響元Pascal(Wirth)、Go(Pike)。クラスも継承もない、Cの正統後継狙う思想
- メモリ管理手動。ただし「まとめて確保・まとめて解放」の塊管理を言語側でサポート

## Rust/Zig/Odin比較

| 言語 | 最優先事項 | 代償 |
|-----|-----------|------|
| Rust | 安全(所有権・借用チェッカー) | 学習負荷・書きにくさ |
| Zig | 制御の鋭さ(comptime等) | 仕様まだ流動的 |
| Odin | 単純さ・素直さ | 目玉機能なし、地味 |

Odinは安全装置も派手な仕掛けもあえて持たない。仕様は早期安定化済み。

## 目玉機能なし思想

- 作者本人「これといった目玉機能はない」と明言、欠点と思っていない
- 派手な宣伝せず地味な不便を一つずつ潰す方針
- パッケージマネージャすらあえて持たない(「道具はシンプルであるべき」思想)

## ゲーム/グラフィックスで刺さる理由

- データ指向設計(DOD)と相性良い
- `#soa`という言語組み込み構文でAoS→SoA変換をコンパイラがやってくれる(他言語だと手動)
- クラス継承・vtable無し→構造体が素直にフラットなメモリレイアウト
- `[3]f32`等のベクトル型が組み込み、swizzle操作もサポート、SIMDに落ちやすい
- `context.allocator`でアリーナ/プールアロケータへの切替が容易
- 実例: EmberGen(炎/煙リアルタイム生成)は全部Odin製。Bethesda/Capcom等が採用。姉妹ソフトJangaFXも全Odin
- OdinコンパイラはOdin自身で書かれ、C++的なコンパイル遅延がない→試行錯誤速い

## 結び(動画の主張)

Nim(上へ機能追加)とOdin(横へ機能を削ぐ)は正反対だが両方本気でCに挑戦。優劣問題でなく思想選択の問題。

## 補足Q&A(視聴後の疑問と回答)

### 結局Rust使った方が良いのでは

- 仕事・キャリア用途→Rust一択。採用実績(AWS, Discord, Linuxカーネル, Microsoft各所)、crates.ioエコシステム、求人・学習リソース量が桁違い
- 趣味でCの手軽さ求めるだけならZigの方がまだ現実的。TigerBeetle/Bunが採用、コミュニティOdinより大きい
- Odinはゲーム/グラフィックス系ニッチ用途以外で選ぶ理由薄い。パッケージマネージャ無しは長期メンテ前提のプロダクトに不向き

### 「今すぐ動くツール作れる」の中身

Odinの速さは2種類ある、混同注意。

1. コンパイル速度: 本物。ミリ秒〜低秒台。「直して即試せる」の実感はゲーム開発の反復作業と相性良い
2. 「今すぐ動くツール作れる」の意味: 個人が手元でサクッと試作できる、であって「プロダクトとしてすぐ配布できる」ではない。依存管理は全部手動、共有・チーム開発・長期保守には向かない

同種の体験欲しいならGo(コンパイル速い・シンプル・エコシステムは桁違いに大きい)の方が実務では現実的な代替候補。

### データ指向設計(DOD)とは

「もの」でなく「データの並び」を中心に設計する考え方。OOPの逆。

- OOP的: `Enemy{position, health, ai_state, ...}` をオブジェクト単位でまとめる
- DOD的: `positions[]`, `healths[]`, `velocities[]`と種類ごとに配列を分ける
- 理由: CPU計算速度 >> メモリ読み出し速度がボトルネック。キャッシュラインに必要データだけ詰めて連続処理すれば待ち減る

### ECSとの違い

- ECS(Entity Component System): アーキテクチャパターン。Entity=ID、Component=データ、System=処理、と役割分離する設計思想
- DOD: メモリレイアウトの最適化手法(SoA)
- 関係: ECSを実装する際、各ComponentをSoAで持たせると自然にDODになる(Unity DOTS、Bevy ECS等)。ただし逆は成立しない、DODやるのにECSは不要

### AoS / SoA

- AoS(Array of Structs): `struct{x,y,z} arr[100]` — 1個体分まとめて配列化。普通の書き方
- SoA(Struct of Arrays): `struct{ x[100], y[100], z[100] }` — 同じフィールドだけ集めて配列化。DODが使う形

### vtableとは

virtual table。C++/Java等の継承・多態(オーバーライド)実現する仕組み。オブジェクト先頭に「関数ポインタ表へのポインタ」を持たせ、関数呼ぶ時その表経由で間接ジャンプする。この間接参照がキャッシュミス誘発しやすく、CPU分岐予測も効きにくい。DODが嫌う要素の代表。

### Odinのメモリアロケーションは手動か

デフォルト手動(Cのmalloc/free相当)。GC無し。`context.allocator`でアリーナ/プール/一時アロケータへの切替が可能、「まとめて確保・まとめて解放」パターンがやりやすい構造。

### Rust/Go/Node.jsでもDOD設計できるか

できる。DODは言語機能でなく設計パターン。手動でSoA構造書けばどの言語でも実現可能。

- Rust: bevy(人気ECSフレームワーク)がDOD前提の設計。相性良い
- Go: sliceでSoA組める。ただしGC挟むのでOdin/Rustほどメモリレイアウトの完全制御は効かない
- Node.js: `Float32Array`等のTypedArrayでSoA的レイアウト可能。JSエンジンの動的型付け・GC・JITの制約で制御力は劣る。本気でやるならWasm経由

Odinの`#soa`は「専用構文で楽に書ける」利便性の差であって、専売特許ではない。

### SoAで何が効率化するか(コード例)

```c
// AoS: 普通の書き方
typedef struct {
    float x, y, z;      // position
    float vx, vy, vz;   // velocity
    float health;
    int   ai_state;
} Enemy;

Enemy enemies[10000];

for (int i = 0; i < 10000; i++) {
    enemies[i].x += enemies[i].vx;
    enemies[i].y += enemies[i].vy;
    enemies[i].z += enemies[i].vz;
}
```

1体32byte。position更新に要るのはx,y,z,vx,vy,vz(24byte)だけなのに、health・ai_state(不要な8byte)も同じキャッシュラインに載る。64byteのキャッシュラインに2体分弱しか入らず、無駄なデータのために帯域を消費。

```c
// SoA: フィールドごとに配列分離
typedef struct {
    float x[10000], y[10000], z[10000];
    float vx[10000], vy[10000], vz[10000];
    float health[10000];
    int   ai_state[10000];
} Enemies;

Enemies enemies;

for (int i = 0; i < 10000; i++) {
    enemies.x[i] += enemies.vx[i];
    enemies.y[i] += enemies.vy[i];
    enemies.z[i] += enemies.vz[i];
}
```

`x[]`だけ見ればfloatが隙間なく連続。64byteのキャッシュラインにx座標16体分入る。health・ai_stateは別配列なので一切ロードされない。連続アクセスでプリフェッチも効く、SIMDにも掛けやすい。

効いてる要因: ①使わないデータをキャッシュラインに巻き込まない ②連続メモリ読みでプリフェッチ効く ③SIMDベクトル化しやすい。3つ合わさって大量オブジェクト処理で数倍〜数十倍差が出ることもある。

### 効果を実感できる規模感

- 数十〜数百: 差はほぼ誤差
- 1,000〜1万: 差が測定可能になり始める領域(構造体サイズ小さいほど下限上がる)
- 1万〜10万以上: はっきり体感できる領域、数%〜数十%の差

キャッシュ的理由: L1キャッシュは大体32〜48KB。軽量構造体(position+velocity程度、16〜32byte)ならL1だけで1,000〜2,000個収まる、数千程度だとまだ差出にくい。

具体例:
- 弾幕STG(東方等): 弾丸1,000〜数万発同時、効果出やすい代表例
- パーティクルエフェクト(爆発・煙・火花): 数千〜数十万個、DOD/SoAほぼ必須級
- RTS大規模戦闘: ユニット数百〜数千
- 群衆シミュレーション: 数千〜数万

逆にプレイヤーキャラ・主要NPC本体のような「複雑だが数少ない(数十〜数百)」対象はAoSのままでも大差なし。DODが刺さるのは「単純な構造体を大量に同じ処理で回す」パターン(弾丸・パーティクル)。
