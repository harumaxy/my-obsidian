出典: 『流暢なReact』(Fluent React) 9章

## RSC 何者

サーバのみ実行コンポーネント。クライアントJSバンドルから除外。ビルド時実行、ファイル読取・DBアクセス等可。

利点:
- サーバ計算 → 予測可能パフォーマンス
- セキュア環境実行 → トークン等安全に扱える
- 非同期実行 → サーバ完了待ってからクライアント送出

## 仕組み 2段構え

1. RSCsレンダラー: コンポーネント関数 → React要素ツリー(オブジェクト)変換。子コンポーネント再帰呼出、`await`も処理
2. サーバレンダラー: 要素ツリー → HTML文字列/ストリーム変換（初回ロード時のみ）

要素ツリーはSymbol値持つため素の`JSON.stringify`不可 → replacer関数でSymbol↔文字列変換要

## ナビゲーション（ソフト遷移）

リンククリックをイベント委譲で捕捉 → `fetch`で新ページのJSXツリー要求 → デシリアライズしrootへ再レンダリング。フルリロード回避。

ただしトイ実装ではページ単位で丸ごとツリー再取得。個別コンポーネント狙い撃ち取得ではない。

## サーバ/クライアント分離ルール

サーバコンポーネント制約:
- props全部シリアライズ可能必須（関数不可）
- 有効フック不可（useState/useEffect等。useRefは可）
- state = クライアント間共有的、ローカル状態向かず
- クライアントコンポーネントはサーバコンポーネントimport不可（childrenとして渡すのは可）

`"use client"` でクライアント境界指定。次世代バンドラーがサーバグラフ/クライアントグラフ分割、クライアント部分は「モジュール参照」プレースホルダーとしてツリーに埋込→クライアント側で実モジュールに解決。

誤解訂正: クライアントコンポーネントも初回はサーバ上で一度実行される（SSR時）。以降クライアントのみ実行。サーバコンポーネントはクライアントで一切実行されない。

## サーバアクション

`"use server"` でクライアントから呼べるサーバ専用関数マーク。`<form action={fn}>`でJS未ロード時も送信可（progressive enhancement）。`useTransition`と組合せフォーム外呼出も可。

## 従来フルSSRとの差（Q&A整理）

比較:
- 送信物: 従来=HTML文字列 / RSC=シリアライズ要素ツリー
- バンドルサイズ: 従来=全コンポーネント含む / RSC=サーバ専用コード除外→小
- 更新粒度: 従来=ページ単位 / RSC=コンポーネント単位DOM差分（React通常reconciler）
- データ取得: 従来=クライアント側waterfallあり得る / RSC=サーバ内でawait完結、往復減

**サイズ差の誤解注意**: 素のJSON表現はHTML文字列よりむしろ大きくなりがち（`$$typeof`等冗長）。本番実装(Flight形式)は専用圧縮フォーマットで軽量化。

**速さの本質はペイロードサイズでなくラウンドトリップ削減**。クライアント側で「mount→fetch→ローディング→再レンダリング」のウォーターフォールが起きず、サーバ内でデータ取得済の結果を1回で受け取る。

**「部分的データ取得」の実態**: 本章のトイ実装はページ全体のツリー再取得なので厳密には部分取得でない。真の部分取得（セグメント単位fetch・キャッシュ・Suspense境界ストリーミング）はNext.js App Router等フレームワーク側の踏み込んだ実装、本章の範囲外。

## コンポーネント単位という言葉の3レイヤー整理

1. ネットワーク取得粒度: 本章実装はページ単位（コンポーネント単位でない）
2. DOM更新粒度: コンポーネント単位（Reactの通常reconciler差分）
3. JSバンドル分割粒度: コンポーネント単位（`"use client"`境界ごとにモジュール分離、遅延ロード）

「コンポーネント単位」と一括りに言うと3つを混同しやすい、要注意。
