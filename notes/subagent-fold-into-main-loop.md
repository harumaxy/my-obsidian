## 結論

- 「サブエージェント使うな」ちがう。「最初から分けるな。まず単一ループ。測って、一個ずつ畳め」。
- 記事の結び: "measure, change one thing at a time, and keep what holds up."
- 統合版のスコア負けたら、そのサブエージェントは残す。

## 記事の主張

- 企業導入で、ルーター・プランナー・ドメイン別サブエージェントを単一ループ + 段階的開示 (スキル + ツール検索) に畳むと、品質・コスト・速度が良くなること多い。
- 多エージェント化の失敗パターン
  - 組織図そのまま複製 (コンウェイの法則)
  - 受け渡しでコンテキスト劣化 = 伝言ゲーム
  - サブエージェント乱立、持ち主なし
  - プロンプト継ぎ接ぎ → ルール矛盾
  - 評価が局所最適
  - 遅い。ある顧客は単一ループが約2倍速
- 単一ループが効く理由
  - 共有コンテキストで洞察が深い
  - スキル/ツール検索で必要時だけロード → 肥大しない。Claude Code はシステムプロンプト 80% 以上削減
  - 判断をハーネスからモデルへ移せる。次モデル移行も楽
- 条件: システムプロンプト管理、スキル説明の発火設計、中央の小チームが E2E 品質に責任

## サブエージェント残す場面

- 並列実行したい + 使い捨てコンテキストが欲しい
- 単一ループで、コンテキスト肥大による劣化を実測した
- ツール選択が難しい、指示が矛盾する
- 分割は「問題の種類」でなく「コンテキスト」で切る。独立していて小さい結論だけ返す作業が向く

## 畳む手順

1. タスク完了型 eval を作る。10 件程度の正解例からでよい
2. サブエージェントを「ツール」として呼ぶ。会話の主導権は主エージェント。全面引き継ぎはサブエージェントがユーザーと直接話す時だけ
3. 一個ずつスキル/ツールに置換。前後比較。スコアだけでなく「どのタスクの結果が変わったか」を見る
4. 密接に連携する専門家から畳む (出力連鎖、同データ、よく一緒に呼ぶ)
- 失敗例: サポートエージェントで注文照会を直接やらせたら配送日確認が消えた。失敗率は 2 回に 1 回。eval は複数回走らせる

## 複数チームの貢献方法

- MCP ツール: API 単位でなくユーザー意図単位。30〜50 超で選択精度落ちる。権限チェックはツール側
- スキル: チームの仕事の流儀。DRI が持つ
- ナレッジベース: 検索ツール or スキル内参照ファイル。コードで文脈抜いてプロンプトに貼るのは避ける

## 具体例で考える

アンチパターン = 工程・役割で分割。途中経過と判断理由が落ちる。

- 開発: 要件 → 設計 → 実装 → テストを別エージェント。実装が設計の意図を要約でしか受け取れない。テストが仕様の背景を知らず的外れ
- 調査: 検索 → 読解 → 要約 → 批評 → 清書。読解の「怪しい」という違和感が消える。清書役は元資料を見ない
- 改善: 1 エージェントが一気通貫。ルールはスキルにする

正解 = 独立していて、結論が小さく、途中経過は捨てたい作業。

- 呼び出し元を全部洗い出す
- 3 案を並列で試作
- 別の目で diff レビュー
- A/B/C 社を同時に調べて各 300 字
- 100 ページ PDF から該当箇所だけ抜く

判別の目安

- アンチパターン: 分割した作業同士が同じ情報を必要とし、互いの途中経過を知りたがる
- 正解: 独立。小さな結論だけ返せばよい。途中経過は捨てたい

## レビューは別エージェントで良い

- ブラックボックス検証の典型。実装者の思い込みを引き継がない
- 設計→実装は「意図」を渡すので劣化する。レビューは意図を渡さない方が価値あり。渡す物は diff で、欠落しない
- 修正は主エージェントが続ける。会話の主導権は渡さない
- 渡しすぎると独立性が消える。最低限の仕様だけ

## issue 単位の並列エージェント (ready for agent ラベル) もあり

- issue が主題・スコープ・完了条件を持つ = コンテキスト独立。成果物は PR で小さい
- 条件
  - issue 間が独立。同じファイル・同じ設計判断に触れると衝突
  - ラベルは人間が「単独で完結する」と判断してから付ける。ここが品質の要
  - 完了条件をテストで機械確認できる
  - worktree / ブランチを分ける
  - CLAUDE.md やスキルは全員共有
- 設計判断を含む issue は向かない。設計は先に決めて issue に書く
- 並列を増やすとボトルネックは実装からレビューへ移る

## なぜアンチパターンが広まったか (推測。記事の記述ではない)

- 初期モデルは短コンテキスト・長指示に弱い・ツール多いと迷う。分割は当時は合理的な回避策。回避策が設計思想として残った
- 擬人化の比喩 (PM・設計者・実装者・テスター) は説明しやすく、デモ映えする。MetaGPT、ChatDev、CrewAI の役割ベースがこの系統
- 作る側の組織都合が設計に出る (コンウェイの法則)。担当が明確だと管理・説明しやすい
- エージェント 5 体のログは仕事してる感じがする。eval がないと悪化に気づけない
- 人間の分業は「人間の制約」(1 人の頭に入らない、並行できない、専門習得に年数) への対処。LLM に持ち込んでも合わない
- ビジネスサイド限定でなく、エンジニアの「単一責任」「責務の分離」感覚、マイクロサービス流行と同じ構図。粒度が細かすぎると通信コストが利益を上回る

## フルスタックの感覚

- 人間でも FE・BE・テストを 1 人で書く方が速いことが多い。内部事情を知っているから、境界の調整がその場でできる
- 分業が効くのは、接続面 (インターフェース) が小さく安定している時だけ
- エージェントを分ける時の問い: 「このインターフェースは小さく固定できるか」
  - 小さく明確: 独立調査、別リポジトリのライブラリ、issue 単位の機能追加 → 分けてよい
  - 太い、または変わり続ける: UI と API、実装とそのテスト → 分けると伝言ゲーム

## 自分の使い方との照合

- 設計・実装・テストは 1 エージェント一気通貫、レビューは別エージェント、独立チャンクは並列。記事の方針と一致
- 学びは薄い。使えそうな点
  - eval で測る。体感でなく
  - スキル/MCP の肥大管理。ツール 30〜50 超で選択精度低下。使ってないスキル・プラグインは削る
