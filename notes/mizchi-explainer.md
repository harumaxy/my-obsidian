- 入れ方: `/plugin marketplace add mizchi/explainer` → `/plugin install explainer@explainer`

- 依存: Node 24+、`npm i -D @mizchi/vlmkit marked playwright mermaid`。D2 図は `d2` CLI、形式手法の例は Java と TLC / Apalache / z3。
- SKILL.md 本文は日本語。README は英語と日本語。

## 思想

- エージェントの書く速度に、人の理解が追いつかない。理解が律速 (Geoffrey Litt の "Understanding is the new bottleneck" を引用)。
- 読み手 1 人に、**その人がまだ知らないことだけ**を書く。
- 書いた主張と図は**道具で検証**する。「書いていて自信がなくなる」を「検査の緑」に置き換える。
- ELI5 との違い: ELI5 は読み手を型 (年齢・職業) で扱う。こちらは実在の 1 人をペルソナにし、検査もする。

## スキル 5 個

- `explainer` (253 行) ... 1 人の読み手向けの速習資料。本命。
- `explainer-book` (124 行) ... 章立ての講座。学習目標と小テストの対応、概念の導入順、章ごとの読了時間、演習 (出発点は失敗し、答えは通る) を検査。読了 20 分超、演習が要る、概念に順序がある場合に使う。
- `first-reader` (306 行) ... 下書きを、模擬読者に 1 段落ずつ読ませる。離脱箇所と翌日残ったものを報告。**書き直しはしない。** Shubhamsaboo/awesome-llm-apps から同梱 (Apache-2.0)。日本語の段落分割に対応させた。
- `d2-diagram` (436 行) ... TALA レイアウトの D2 図。ターミナルで確認し、`d2-facts.mjs` の事実シートと照合。
- `d2-slides` (290 行) ... 図ごとに D2 を書いた Markdown 1 本からスライド HTML を作り、vlmkit のゲートで検査。

最後の 2 つは mizchi/vlmkit 由来。`explainer-book` は `explainer` の `verify-doc.mjs` を使うので、`explainer` / `explainer-book` / `first-reader` はセットで入れる。

## explainer の手順

1. ペルソナ: `personas/<id>.md` を読む。無ければ、質問する前に仮ファイルを書く。材料は質問 (最大 5 問) と公開情報 (主張ごとに URL、事実と推測を分ける)。
2. 問いを絞る: 読み手が読み終えて判定できるようになること 1〜3 個。
3. 差分を決める: ペルソナの「知っている」は書かない。「怪しい」を芯にする。
4. 実物を作る: 主張ごとに、動く例 (コード・モデル・コマンド) を先に走らせる。
5. 書く: 価値を先に、根拠は後に。出力は貼る (打ち直さない)。削除テストと「読みやすい日本語」の点検。
6. 図: 事実シートを先に、図は後。Mermaid か D2。
7. 検証: `verify-doc.mjs` が VERIFIED になるまで。
8. 読ませる: `first-reader` でペルソナ本人を読み手に。
9. 渡す: HTML と要約。検証できなかったことは「未検証」と明記。

- **推測を事実として扱わない**ルールが強い。依頼文にない経歴は事実の欄に書かず、「推測した + 理由」と分ける。質問して止まる場合も、先にペルソナの仮ファイルを書く。返答の型まで SKILL.md に固定されている。
- 検証の中身: 本文に引用した出力は `checks.json` から再実行して照合。図は fact sheet と照合し、重なり・見切れ・矢印の読みやすさを `figure-check.mjs` で検査。HTML は vlmkit の integrity / a11y contrast。

## 付属の成果物

- 例: mizchi 本人向けの形式手法 (Z3 / TLA+) 速習資料。公開情報からペルソナを作ると「初心者ではなく、既にエージェント経由で約 10 個の検証器を回している」と分かり、「検証器の緑が何を保証したかを自分で判断する基準」に絞った。
- 例: 「帰納的不変条件を自分で見つける」3 章の講座。
- 例: 図ツール選びのチートシート。Mermaid / D2 の 3 エンジン (TALA / ELK / dagre) を同じ図で比較。実測の知見として、コンテナ内の `direction` は Mermaid では内部ノードが外へつながると無視され、ELK / dagre では常に無視され、TALA だけ守った。TALA はシードで配置が大きく変わり、ボックスが増えると急に遅くなる。
- 補助スクリプト: `tlc-to-mermaid.mjs` (TLC の状態グラフ → Mermaid)、`icons.mjs` (Iconify のアイコン検索と出典記録)、`figure-variants.mjs` (配置候補をスコア付きで並べる)。
- 日本語文書では yomiyasu (未同梱) を入れると、AI 臭い日本語のパターンを `verify-doc.mjs` が指摘する。

## 所感

- 発想が違うのは、他のスキルが「AI の出力を整形する」のに対し、こちらは「検証した事実だけを、読み手の差分で渡す」ところ。説明資料・PR 解説・設計レビュー資料を AI に作らせる場面が多い人向け。
- 重い。Node 24 + Playwright + (Java / D2 / z3) と、準備が大きい。軽い説明には過剰。
- 取り入れる価値が高いのは、仕組み全体より次の考え方。自作の指示やスキルに足せる。
  - 読み手を 1 人決め、知っていることは書かない。
  - 推測は事実と分けて書く。
  - 書いた本文の主張・出力は再実行して照合する。
  - 下書きを模擬読者に読ませて離脱箇所を見る (`first-reader`)。
- このリポジトリの用途 (自分用の要約メモ) では、検証パイプラインは不要。技術記事の要約で「事実と所感を分ける」習慣の参考にはなる。
- 導入判断: 見送り。説明資料を量産する案件が出たらプロジェクト単位で再検討。`first-reader` 単体は軽そうなので、文章の推敲用に興味が出たら試す。

## A/B 実測 (2026-11-08、構成図 + データフロー図つき解説資料)

小さな注文サービス (Hono + TS、13 ファイル) を題材に、素の Claude と explainer スキル読込のサブエージェントを同じ依頼で並列実行。各 2 回。成果物は容量が大きいので削除済み。残したのは比較画像 `~/workspace/diagram-ab/compare-run2.png` のみ (2 回目の図を 2 × 2 で並べたもの)。数字はサブエージェント自身の報告と実行ログ。

- 所要 (2 回目、セットアップ引き継ぎ後): 素 約 3.9 分 / 9.2 万トークン / 20 回 vs スキル 約 15 分 / 20 万トークン / 70 回。1 回目は素 2.5 分 vs スキル 10.5 分 (依存取得込み)。セットアップを除いてもスキル側は遅い。
- 時間の使い道 (スキル側): 図の描き直し (構成図 3〜4 回 → 手書き SVG へ切替)、実行ハーネス作成と 8 シナリオ実行、模擬読者の通読と用語表追加、`verify-doc.mjs` 通過。
- 中身: どちらも指摘の種類はほぼ同じ (冪等性なし、他人の注文が読める、決済失敗でも paid、ジョブ消失など)。スキル側は実コードを動かして実測値を本文に貼り、未検証を表に分け、理解度チェックとチェックリストを付けた。素は読んだだけで再現なし。
- 図: 素はシーケンス図 + 凡例つき構成図。スキル側は import 依存の図 + 縦フローチャート。好みは分かれる (自分はスキル側がシンプルで見やすいと感じた)。
- データフロー図の形式差は好みでなく道具都合: スキル側は最初シーケンス図で描いたが `figure-check` が辺を検査できず、検査可能なフローチャートへ変更した。
- 結論: 時間差が大きく甲乙つけがたい。スタイルは素への指示でも寄せられそう。スキルの本当の差は「実コードを動かして出力を貼る」「未検証を分ける」「理解度チェック」の規律。核の 3 点だけ素に指示で足した 3 本目の条件は未実施 (やるなら次)。
